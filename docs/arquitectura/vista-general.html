01Principios

Cuatro reglas gobiernan todo el código. Ninguna se rompe sin una decisión explícita del dueño.

Determinística primero

La lógica contable es código normal con reglas explícitas, auditable línea por línea. La IA se reserva para leer documentos (Módulo 3, aún no construido) y nunca decide un asiento. El chatbot de WhatsApp es 100 % determinístico.

Arquitectura por features

Cada parte del programa es una carpeta autocontenida —router, service, schemas, models— con una carpeta de documentación espejo. Se audita y se mantiene una feature a la vez.

La lógica vive en el servicio

Toda regla de negocio está en los service.py. Los router.py solo traducen HTTP. Los servicios lanzan errores de dominio, nunca HTTPException: app/main.py los traduce.

Un solo punto de escritura contable

Nadie toca las tablas asiento / linea_asiento sin pasar por crear_asiento(), que valida la partida doble (débitos = créditos) antes de guardar.

Async en todo desde el inicio (FastAPI, SQLAlchemy, httpx, pytest). El motor contable solo no lo necesita, pero el Módulo 2 y la IA sí, y tener un único estilo sale más barato de auditar.

02Las capas

Toda petición atraviesa las mismas capas, siempre en el mismo orden. Cada una tiene una responsabilidad y una prohibición.

Transporte
Router de FastAPI o webhook de WhatsApp. Valida el formato con Pydantic, llama al servicio, traduce el error de dominio a HTTP.
app/**/router.py · app/main.py  —  no decide nada de negocio
↓
Servicio de feature
Toda la regla de negocio. "Una factura recibida genera este asiento." Funciones async. Lanza NoEncontrado, Conflicto, DatosInvalidos.
app/features/<feature>/service.py  —  no arma respuestas HTTP
↓
Núcleo contable
crear_asiento() valida el cuadre de partida doble y el documento de soporte. calcular_balance() es una sola consulta SQL de agregación con filtros de libro, periodo y actor.
app/contabilidad/  —  único que escribe en las tablas contables
↓
Modelos (SQLAlchemy)
Las tablas como clases Python. Relaciones cargadas de forma explícita (lazy="selectin"), nunca perezosa —lo prohíbe async.
app/**/models.py · app/models.py (agregador)

Cuando el Módulo 2 (WhatsApp) necesite registrar una factura, llamará a facturas.service.registrar_factura(...) —la misma función que usa la API—, no reimplementará la lógica.

03Flujo de una petición

Ejemplo: POST /facturas con una factura recibida de $500.000 + $95.000 de IVA.

  1. FastAPI recibe el JSON y lo valida contra el esquema FacturaCreate. Falta un campo o tipo equivocado → 422 automático.

  2. El router facturas/router.py pide una sesión de base de datos (Depends(get_db)) y llama a facturas.service.registrar_factura(session, ...).

  3. El servicio verifica que el tercero exista (si no → NoEncontrado → 404), calcula total = subtotal + iva en el servidor, y arma las tres líneas del asiento según la tabla de reglas de la feature.

  4. Llama a contabilidad.asientos.crear_asiento(...) con el tercero_id. Este valida que Σ débitos = Σ créditos. Si no cuadra → AsientoDesbalanceado y no se guarda nada.

  5. El servicio guarda la factura enlazada a ese asiento y hace commit. Registra en el log: Factura F-001 registrada — #3 total=595000.00.

  6. El router devuelve la factura creada como JSON (FacturaOut). Si algo falló de forma inesperada, app/main.py responde 500 con un mensaje genérico y el traceback queda en el log —el servidor sigue vivo.

07Base de datos

SQLite (un archivo) para desarrollo, PostgreSQL para producción. Se cambia una línea —DATABASE_URL en el .env—; ningún código se toca, todo pasa por el ORM async. El esquema se crea con migraciones Alembic, no con create_all: un test verifica que los modelos y las migraciones no se separen.

Códigos inspirados en el PUC colombiano para no chocar con la DIAN más adelante. La naturaleza (deudora / acreedora) determina el signo del saldo: deudora = débitos − créditos; acreedora al revés.

Los dos libros

Cada asiento pertenece al libro oficial (contabilidad real, exige documento de soporte, cuenta para la DIAN) o interno (para-contabilidad: retiros informales, préstamos sin papeles). El balance por defecto solo suma el oficial; ?libro=todos muestra la caja "real".

08Resiliencia y logs

Errores

De dominio (404/409/422) → mensaje claro, log INFO. Inesperados → 500 genérico sin filtrar internos, traceback en el log, el servidor sigue vivo. Datos inválidos → 422 con detalle.

Transacciones

Una por petición. Si el servicio falla, get_db hace rollback antes de cerrar: nunca queda un asiento suelto.

Base de datos caída

El pool de PostgreSQL usa pool_pre_ping. Al arrancar, si la BD no responde, la app arranca igual, lo deja en el log y /salud responde "degradado".

Logs

Todo a stdout, formato único, loggers elgerente.<área>. Una línea por petición y por hecho de negocio. La contraseña de la BD nunca aparece.
